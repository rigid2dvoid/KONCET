# ADR-0007: GPL-3.0-or-later Licence

> **Status:** Accepted · **Date:** 2026-11-24

## Context

KONCET is intended as a long-lived public portfolio and learning product. The maintainer wants
to keep derivative desktop distributions open, allow community improvement, and preserve the
project's identity. The project is an application, not a library with broad proprietary
adoption goals. It is distributed from GitHub and embeds third-party open-source components.

## Decision

License the project under the **GNU General Public License, version 3 or later**
(`GPL-3.0-or-later`).

- The canonical GPLv3 text is in `LICENSE`.
- Source files will carry SPDX headers where practical; release artifacts include the licence,
  source link, and third-party notices.
- Contributions are inbound=outbound under GPL-3.0-or-later; no separate CLA.
- Dependencies must be GPL-3.0-compatible; automated licence checks gate merge and release.
- The “or later” option is intentional, following the FSF recommendation and allowing future
  GPL versions if they preserve user freedoms.

## Consequences

**Positive:** modifications distributed to users must remain open; protects the portfolio
project from proprietary forks; aligns with the open learning mission; encourages contributions
back; simple single-licence story.

**Negative:** cannot be linked into proprietary products; some companies avoid GPL; licence
compliance work for dependencies and notices; GitHub itself is not the licence, and forks can
still diverge under the same terms.

**Mitigations:** clear `CONTRIBUTING` and `SECURITY` documents; SBOM and notices; licence
training links; test and release gates; no dependency with unclear terms.

## Alternatives considered

- **MIT/Apache-2.0:** maximum adoption but allows closed derivatives, contrary to the protection
  the maintainer wants.
- **AGPL-3.0:** adds a network-use clause that is unnecessary for an offline desktop app and may
  create confusion for contributors.
- **Source-available/non-commercial:** not an OSI licence, limits community use, and conflicts
  with the intended open-source portfolio.
- **Dual licensing:** unnecessary complexity for a project with no commercial licensing plan.
